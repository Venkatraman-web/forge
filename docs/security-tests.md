# Security tests of our own deployment (2026-11-01)

Scope: Forge and ForgeCart as deployed on our own AWS machines (private network, plain HTTP, no TLS), the repository, and the machines' configuration. Nothing outside it was touched. The tests were non-destructive; the few jobs and orders they created were removed or left to expire. The scripts are in `~/.forge-aws/` (`sec_exposure.sh`, `sec_auth.py`, `sec_input.py`, `sec_cart.py`), not in the repository. This is a first round, not an audit: it says what was tried and what happened, and it is not a claim that Forge or ForgeCart is secure.

| Area | What was tried | Result |
|---|---|---|
| 1. Exposure | TCP connections from my laptop (on the internet) to 17 ports of each of the 8 machines; later (2026-11-01) the AWS security group was read with read-only calls | Only port 22 (SSH) answered, on all 8. Correction after reading the security group `forge-bench`: SSH is **not** open to the whole internet. The group allows TCP 22 only from **four specific /32 addresses** (my laptop's address is one of them, which is why the scan saw it open), plus all traffic from members of the same group; no other port is open to any outside address. Forge's 8080/8081/8082, the shop's 8090, PostgreSQL and the metrics ports are therefore closed from outside. SSH accepts keys only (password and keyboard-interactive logins are off, root login without a password). Also seen: instances require IMDSv2, have no IAM instance profile and no Elastic IPs (public addresses change on every start); the EBS volumes are **not encrypted**. A scan from an address that is not on the list was not run. |
| 2. Authentication and roles (Forge's three APIs, from inside the network) | 33 requests: no key, wrong key, the other roles' keys, empty bearer, Basic scheme, no scheme, key in the query string or a cookie, a 7 KB header, wrong paths and methods | 33 of 33 as expected: `401` with the same generic body in every case, `/health` is the only open path, each role's key is refused by the other two APIs, the right key works. |
| 3. Input handling (Forge's submit API) | 41 requests: malformed, empty and array bodies, unknown fields, missing fields, SQL/control characters/10 KB in the job type, 2 MB body, 100,000-level nesting, bad `max_attempts` and `timeout_seconds`, bad idempotency keys, hostile job ids and list parameters, batches of 0 and 101, wrong methods | 40 of 41 at first. The failure: `GET /v1/jobs/{id}` with a NUL byte in the id answered `500` (PostgreSQL rejected the byte). Not an injection (ids are parameters; the SQL-text ids got 404). Fixed in commit `0c19b1c`: an id that cannot be one of ours is a 404 without a database call; 41 of 41 afterwards. |
| 4. Information leakage | Error bodies, response headers, Forge's log of two hours | Errors are one small JSON shape with no stack traces and never echo the submitted input; no `Server` header; the log holds no database URLs, passwords or keys (the only "Bearer" lines are the startup banner) and none of the hostile strings sent. |
| 5. ForgeCart | 32 requests: price/total sent by the client, quantities 0, -1, 101, 2^31, 2^63, 1.5, string, null, duplicate and 21 SKUs, SQL/hostile SKUs and e-mails, missing/short idempotency keys, key reuse, hostile order ids, a 2 MB body; the payment service and the shop metrics without keys | 31 of 32: the total always comes from the catalogue; bad quantities, SKUs, e-mails and ids get clean 400/404; the same key and request returns the same order and a different request gets `409`; the payment service listens on loopback only and answers `401` without a (or with a wrong) key; the shop metrics ports answer `401`. The failure: a 2 MB body to `/v1/orders` ended in a connection reset on the client instead of a `413`. Reading the code afterwards: the shop already answers `413 request_too_large` when a body passes its limit (16 KB); Go's server discards only a small part of an oversized body before closing the connection, so a client still sending megabytes can see the reset before it reads the answer (Forge's limit is 1 MB, so the same 2 MB test got its `413`). This is standard behaviour, not changed (draining more would help a flood, not a client); a body just over 16 KB should get a clean `413`, which has not been run yet. Also: paths without a route (for example `GET /v1/orders/{id}`) answered in plain text ("404 page not found"); fixed afterwards in the shop and the payment service (a catch-all route answers `404 not_found` in the JSON error shape; built and vetted, **not yet run against the machines**). |
| 6. Secrets | Tracked files and the whole git history for URLs with passwords, key-like assignments and key files; file modes on the machines | No secret in the tracked files; the only database URLs in history are placeholders (`PASSWORD`, `YOUR_PASSWORD`, `CHANGE_ME_before_first_start`); `.env` is ignored; the env files on the machines are mode 600; the local secrets file is mode 600. (The test and benchmark scripts pass database URLs on ssh command lines, so they are briefly visible in the process list of the target machine.) |
| 7. Dependencies | Module integrity (`go mod verify`: all verified), then `govulncheck` (run by the project owner; its output was cut off at the message limit partway through the sixth finding, so there may be more) | Six findings seen: GO-2026-6809 (`crypto/x509`, Go 1.26.8, fixed in 1.26.10), GO-2026-6629 (`golang.org/x/text` v0.28.0, fixed in v0.41.0; reached through the PostgreSQL driver), and GO-2026-6617, 6613, 6612, 6611 (`net/http`, Go 1.26.8, fixed in 1.26.9: HTTP/2 server crash, request desynchronization after a CONNECT reply, double flow-control refund, excessive CPU from window changes). `golang.org/x/text` is upgraded to v0.41.0 (with the indirect modules it requires and the `go` directive 1.25.0; build and `go vet` pass). **Decision of the project owner (2026-11-01): the Go toolchain is not upgraded.** The five standard-library findings (GO-2026-6809, 6617, 6613, 6612, 6611) are therefore **not fixed**: they are fixed only by building with Go 1.26.10 or later, and the binaries stay built with 1.26.8. They are accepted for this learning deployment, on the reasoning below, which was not tested. The rest of the scan output (it was cut off) has not been read. That the scanner reports a call path does not mean the problem can be exploited here: the three HTTP/2 server problems need HTTP/2, which Go serves only over TLS (Forge has none) unless h2c is configured (not checked), and our servers answer CONNECT with 405. |

## Known by design, not fixed by these tests
- ForgeCart's shop API has no authentication (documented). Any machine on the private network can create orders and pay for them; it must stay off the internet, which is true today.
- Forge speaks plain HTTP; keys travel in clear text on the private network (Forge logs this at startup).
- Forge is single-tenant: every submit key can read every job.

## Not tested yet
Payment webhook signature checks (the simulator is the provider; the Razorpay webhook is not enabled), TLS in front of Forge, denial-of-service beyond the flood and overload chaos tests, the worker API with forged ownership (fencing is covered by the chaos tests, not attacked), and the standard-library dependency findings, which are accepted unfixed (see area 7).
